上下文窗口实验室

模型一次只能看见窗口里的 token。下面的显存和计算量按 Llama-3-70B 的公开参数真实计算，费用按公开的缓存计价比例计算。

00窗口里有什么

每次调用模型，送进去的不只是你刚打的那句话。系统提示、工具定义、整段历史、每次工具返回的结果、检索来的片段，全都排在同一条长度有限的窗口里。拖动五种内容的长度，看谁把窗口挤爆。

–已占用 ÷ 窗口
–超出窗口的 token
–最大的一块
–留给本轮输出的空间

红色部分进不了模型：要么调用直接报错（prompt is too long），要么你得先把什么东西删掉。注意历史消息和工具结果最容易失控，它们每一轮都在长。

01窗口越长，越贵、越慢

长度不是免费的。KV Cache 那一讲算过：每个 token 在每一层都要存一份 K 和 V，显存随长度线性增长。而注意力里每个 token 都要和前面所有 token 算一次相似度，计算量随长度平方增长。下面用 Llama-3-70B 的公开参数（80 层、64 个 query 头、8 个 KV 头、头维度 128、参数 70.6 B，bf16）真实算。

–KV cache（bf16）

显存是一条直线，注意力计算量是一条抛物线。短上下文时矩阵乘法占大头；到几万 token 之后，注意力的 n² 反超并一路拉开。这就是为什么把一整本书塞进窗口要等很久、花很多钱。

02Lost in the Middle：放在中间的信息最容易被忽略

窗口装得下，不等于模型都看得见。Liu 等人 2023 年把一条答案所在的文档放进 20 篇文档的不同位置，发现模型在开头和结尾表现最好，放在中间时正确率掉到接近不看任何文档的水平。拖动关键事实的位置，看命中率怎么变。

示意曲线（首因 + 近因两段指数衰减）论文实测点（gpt-3.5-turbo-0613，20 篇文档）闭卷：不给任何文档

横轴：关键事实在 20 块内容里的位置（1 = 开头）；纵轴：答对的比例

–当前位置的命中率
–比放在开头低
–比闭卷（56.1%）高

曲线是示意模型：命中率 = 底线 + 首因项 × e−位置/τ₁ + 近因项 × e−(距结尾)/τ₂，参数用最小二乘拟合论文表 6 的五个实测点。它只刻画形状，不是任何现役模型的测量值。结论对上下文工程很实际：最要紧的指令放开头，最新的任务放结尾，别把关键事实埋在一大堆工具结果中间。

03对话不断变长：三种压缩策略

Agent 跑几十轮，历史和工具结果会把窗口填满。到那时只有三条路：截断（删掉最早的）、滚动窗口（只留最近 k 轮）、摘要（把早期内容压成一段总结）。下面模拟一段 40 轮的对话，第 2 轮里用户说了一条关键事实（「项目用 Python 3.12，不能用 3.13」），看三种策略下它还在不在窗口里。

–不压缩：总长度
–截断：关键事实
–滚动窗口：关键事实
–摘要：关键事实

每轮的长度由固定种子生成（用户 100–400 token，助手 200–800 token，约三分之一的轮次带 1 000–5 000 token 的工具结果）。截断和滚动窗口迟早把第 2 轮扔掉；摘要策略在占用超过 80% 时把前一半压成 600 token，并把标记为关键的事实写进去，所以它还在，只是变成了一句总结。注意摘要本身也要调用一次模型，而且会丢细节。

04持久记忆：这次写下来，下次读回来

窗口是工作记忆，会话一结束就清空。要让 Agent 下次还记得你，就得在会话结束前把要紧的东西写到窗口外面（一个文件、一张表），下次开始时再读回来。下面模拟两次会话。

记忆文件只有几行，却让第二次会话一开始就知道用户是谁、在做什么。不读记忆，要么模型只能反问，要么得把第一天的对话整段塞回去。字符数由页内文本直接数出；token 数大致与它成比例（Token 那一讲）。

05Prompt Cache：固定前缀只付一次全价

每一轮的输入都是「同样的前缀 + 新增的一小段」：系统提示和工具定义一字不变，历史只在末尾追加。KV Cache 那一讲说过，前文不变则它的 K、V 就不变，所以服务商可以把算过的前缀存起来，下一轮直接复用，只按很低的价格收「读缓存」的费用。拖三个滑块，看多轮对话的累计费用差多少。

第 t 轮的输入是 前缀 + t × 新增。不用缓存时每轮按全价重算；用缓存时上一轮的全部内容按 0.1× 读回，只有新增的那一段按 1.25× 写入。轮数越多、前缀越长，省得越多。代价是前缀必须一字不差地固定：把时间戳、随机数放在系统提示开头，缓存就全废了。输出 token 两种情况一样，这里不算。
