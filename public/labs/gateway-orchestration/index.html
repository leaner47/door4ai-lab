网关与多 Agent 编排实验室

一个模型不够用的时候，请求要在几个模型之间分流，任务要在几个 Agent 之间拆分。下面每个读数都是页内模拟真实算出来的，模型价格和能力是示例参数。

00路由与成本：先让便宜模型试

三档模型，价格和能力都是示例参数：小档每百万 token 输入 $0.15、输出 $0.60，中档 $1 / $4，大档 $5 / $25；每个请求按 800 个输入 token、400 个输出 token 计费。每个请求有一个难度 d，模型答对的概率是 1 / (1 + e−12(a − d))，a 是模型能力（小 0.35、中 0.60、大 0.85）。「先小后大」：小档先答，同时给出一个自评把握；把握低于阈值就把请求升级到中档，中档再没把握就升级到大档。被升级的请求，前面那几次调用的钱照付。

全用小档全用中档全用大档先小后大（阈值从 0 扫到 1）

横轴：每 1000 个请求的费用（美元，对数坐标）；纵轴：正确率。4000 个请求，种子固定

–全用小档：费用 · 正确率
–全用大档：费用 · 正确率
–先小后大：费用 · 正确率
–先小后大：升到中档 · 升到大档

把握阈值拉高，升级的请求变多，正确率逼近全用大档，费用也往上走；拉到 0 就等于全用小档。自评噪声越大，该升级的没升、不该升的升了，绿色曲线整体往右下方塌：路由省不省钱，取决于便宜模型「知道自己不知道」的能力。

01降级与重试：主模型挂了怎么办

20000 个请求。主模型以一定概率整段不可用（这个请求的所有尝试都会等到超时），可用时每次尝试又有一定概率被限流（HTTP 429，0.2 s 内返回）。限流就按 0.5 s、1 s、2 s 退避后重试；有备用模型时，超时或重试用完就切过去。主模型正常响应的中位数 1.5 s，备用模型 2.2 s、可用率 99.5%、限流概率 2%（示例参数）。

–只有主模型：成功率
–加备用：成功率

–加备用：P95 耗时

重试只救得了限流这种「下一次可能就好」的错误，救不了整段不可用：模型挂了，重试三次就是多等三次超时，成功率不变，P95 反而更难看。备用模型把这部分请求接住；超时设短一点，切换来得更早，尾部延迟随之下降，代价是偶尔把本来会慢慢返回的请求也切走。

02缓存：完全相同的请求不再花钱

10000 个请求，每分钟 10 个。每个请求以「重复率」的概率和之前某个请求一字不差（隔多久重复按指数分布抽，平均 1 小时），否则是新请求。网关的响应缓存按完整请求做键：命中且没过期就直接返回上次的结果，不调模型。每个请求 2800 个输入 token（其中 2000 是固定的系统提示）、400 个输出 token，按示例价 $3 / $15 每百万 token 计。

不缓存响应缓存响应缓存 + prompt cache

横轴：第几个请求；纵轴：累计费用（美元）

–响应缓存命中率
–省下的模型调用
–不缓存：总费用
–响应缓存：总费用
–再加 prompt cache：总费用

两种缓存省的不是一回事。响应缓存只对一字不差的请求有效，命中时整个调用都省了，连等待也没有；prompt cache 对每一次真正发生的调用都有效，但只省重复前缀那部分输入的钱（这里按读缓存 0.1 倍计）。重复率为 0 时只剩 prompt cache 在省钱。

03主 Agent 拆任务：并行能快多少

一个调研任务拆成 n 个子任务，每个子任务要转 4 圈工具调用，每圈带回 1500 个 token 的工具结果、模型输出 150 个 token。单 Agent 一个接一个做，所有结果都堆在同一个上下文里；多 Agent 由主 Agent 先拆分，派给 n 个子 Agent 并行做，每个子 Agent 从干净的上下文开始，先要花几圈熟悉情况（冷启动），做完写一段 500 token 的结论交回，主 Agent 读完所有结论再汇总。

横轴：墙钟时间（s）

–单 Agent：墙钟时间
–多 Agent：墙钟时间
–加速比
–单 Agent：总 token
–多 Agent：总 token

多 Agent 的墙钟时间由最慢的那个子 Agent 决定，所以耗时差异越大，加速越打折。总 token 这一栏不一定是多 Agent 更多：同样的工作量下，单 Agent 每一圈都要把之前所有子任务的结果重发一遍，而子 Agent 只重发自己的；多出来的是冷启动、结论和主 Agent 的拆分与汇总。真实系统里多 Agent 往往更贵，是因为它被允许做更多的事，下一个实验细看。

04上下文隔离：谁的窗口先撑爆

还是实验 03 的任务（冷启动 1 圈），这次看每一次模型调用发出去的上下文有多长。单 Agent 的上下文一路堆高；每个子 Agent 只装自己那一份，主 Agent 只读各家的结论。费用按示例价 $3 每百万输入 token 计，「有 prompt cache」时上一次调用已经发过的前缀按 0.1 倍计。

–单 Agent：最长上下文

隔离最直接的好处是没有哪个上下文会撑爆窗口，也没有哪条关键信息被埋在十几万 token 的中间。费用上，单 Agent 二次方增长的重发量大多是重复前缀，开了 prompt cache 会便宜得多，所以「省 token」本身通常不是拆分的理由；拆分换来的是速度和每个上下文的干净。

05何时不该拆：子任务互相依赖的时候

这是一个示意模型，用来看趋势，不是测量值。n 个子任务，每个耗时 1 个单位；任意两个子任务之间以「依赖程度」的概率存在先后依赖（后一个要用前一个的结果）。单 Agent 顺序做，一切都在同一个上下文里，不丢信息，耗时 n。多 Agent 按依赖关系分批并行，拆分与汇总另花 0.5；每条依赖要靠结论交接，以「交接丢失率」的概率丢掉关键信息，接收方要返工一次（返工再并行补一轮，耗时 +1）。每个点 2000 张随机依赖图。

加速比（单 Agent 耗时 ÷ 多 Agent 耗时）随依赖程度；虚线 = 1

返工率（返工的子任务 ÷ 子任务数）随依赖程度

–当前：加速比
–当前：返工率
–当前：总工作量（单 Agent = 1）
–依赖程度超过多少就不如不拆

依赖为 0 时拆分最划算；依赖越密，能并行的批次越少，交接越多，丢信息返工也越多，加速比一路掉到 1 以下。交接丢失率拉到 0，曲线仍会往下走：那部分损失来自「必须等前一个做完」，跟信息丢不丢无关。
