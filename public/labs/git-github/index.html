Git 实验室：代码的时光机与云端仓库

Git 是装在你电脑上的版本管理工具，GitHub 是存放 Git 仓库、方便多人协作的网站。下面五个实验背后跑的都是真实的 Git 规则，哈希也是真算出来的。从一个文件夹出发，一直讲到多人在 GitHub 上合作。

00先说清楚：Git 和 GitHub 不是一回事

没用过版本管理的人，文件夹里往往是这样的：报告_v2.docx、报告_final.docx、报告_final_改.docx、报告_真的最终版.docx。谁改了哪里、哪一版能用、想退回三天前怎么办，全靠记性。

Git 就是来解决这个问题的。它是 Linus Torvalds（Linux 的作者）在 2005 年写的一个软件，装在你自己的电脑上。它把一个文件夹变成「仓库」（repository），记下这个文件夹的每一次改动：什么时候、谁、改了什么、为什么改。想回到任何一个过去的版本，一条命令就行。不联网也能用。

GitHub 是一个网站（2018 年被微软收购）。它在云端替你保存 Git 仓库，并在上面加了协作功能：多人同步、在线审阅代码（Pull Request）、记录问题（Issues）、每次更新后自动测试和部署（Actions）。这个课程网站就放在 GitHub 上，每次往里推送新内容，Cloudflare 都会自动重新发布。

一个比方Git 像 Word 的「修订记录」，只不过记录的是整个文件夹；GitHub 像网盘，再加上一个大家一起看修订、一起评论的地方。GitLab、Bitbucket、Gitee 是和 GitHub 同类的网站，底下用的都是 Git。

01三个区域：工作区 → 暂存区 → 仓库

Git 里的一个文件可能处在三个地方。工作区就是你看得见、正在编辑的文件。暂存区是「下一次提交要带上的改动」，像是装箱前的清单。仓库里存着一串提交（commit），每个提交是整个项目在某一刻的完整快照。

为什么中间要多一个暂存区？因为你可能同时改了三个文件，但只想把其中两个作为「修好了登录 bug」一起提交，第三个还没写完。git add 决定哪些改动进清单，git commit 把清单打包成一个快照。

试试看：编辑 train.py 和 README.md，只 add 其中一个再提交，然后跑一下 git status，看另一个文件还留在工作区。点仓库里任何一个旧提交，可以看到项目在那一刻的样子，这就是「时光机」。

02每个提交都有一个指纹

你会在 GitHub 上看到 a3f9c21 这样的编号，它是提交的哈希：Git 把内容送进 SHA-1 算法，得到 40 位十六进制数，平时只显示前 7 位。内容哪怕只差一个字符，结果也会面目全非。所以哈希可以当作内容的指纹。

03分支与合并：平行宇宙

想试一个新功能，又怕把能用的代码搞坏？开一个分支（branch）。分支其实就是一张贴在某个提交上的标签。新提交会让当前分支的标签往前挪，其他分支纹丝不动。试成功了就合并（merge）回 main；试失败了，直接把分支删掉，main 不受影响。

实心标签是你现在所在的分支（HEAD）。合并有两种结果：如果 main 在你开分支之后没动过，Git 只是把 main 标签挪到分支最新处，叫 fast-forward，不产生新提交；如果两边都有新提交，Git 会造一个有两个父提交的「合并提交」（双圈），两条线在这里汇合。

冲突如果两条分支改了同一个文件的同一行，Git 不会替你选，它会在文件里把两种写法都标出来，叫「合并冲突」（merge conflict）。你手动改好、重新 add 和 commit 就算解决了。这个实验里假设两边改的是不同的地方。

04本地仓库与远程仓库：push 和 pull

到这里为止，一切都发生在你自己电脑上。GitHub 上的仓库叫远程仓库，习惯上叫 origin。它和你电脑上的仓库是两份独立的副本，不会自动同步，要靠三条命令：git clone 第一次把整个仓库连同全部历史复制下来；git push 把你的新提交送上去；git pull 把别人的新提交拉下来。

你的提交同学的提交合并提交

按这个顺序试一遍：同学先 clone → 你和同学各提交一次 → 你 push（成功）→ 同学 push（被拒绝，因为 GitHub 上有他没有的提交）→ 同学 pull（自动生成一个合并提交）→ 同学再 push（成功）→ 你 pull，三方重新一致。

05在 GitHub 上协作：Pull Request

多人项目一般不允许直接往 main 推送。标准流程是：开分支、提交、把分支推到 GitHub，然后开一个 Pull Request（简称 PR，意思是「请把我的分支合进 main」）。同事在网页上逐行审阅，提意见，你补改，通过后再合并。一步一步看：
