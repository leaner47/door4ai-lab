02模型给的参数可能是错的

  
模型是在「预测下一个 token」的框架下学会输出这种结构的：训练时见过大量带工具调用的对话，于是它学会了在该出 tool_use 的地方出 tool_use。但这是生成，不是执行，所以它可能把类型写错、漏掉必填字段、甚至编出一个不存在的工具名。程序必须先拿 schema 校验，再决定要不要执行。

官方文档的说法是：失败就回一个 is_error: true 的 tool_result，把错误写得可操作，模型一般会改两三次再放弃。更省事的办法是在工具定义里开 strict（OpenAI）或按文档建议约束 schema，让非法参数一开始就出不来。

  






  
03三个工具，串行还是并行

  
模型可以在一次回复里生成多个 tool_use 块（Anthropic 叫并行工具调用，OpenAI 叫 parallel_tool_calls）。这些调用之间没有依赖时，程序可以同时发出去，总时间从「加起来」变成「取最大」。

  

    

      

      

      

      

    

    
    

      
–串行（一轮调一个）

      
–并行（一轮调三个）

      
–省下

      
–模型生成占总时间

    

    
串行方案里模型要来回四轮，每轮都要重新读一遍整个对话再生成；并行只要两轮。把模型耗时滑到 0 看清楚：剩下的差距才是工具本身的延迟差。注意并行只对互不依赖的调用有效，「先查航班号再查这班飞机的天气」只能串行。

  






  
04工具结果太长怎么办

  
tool_result 的内容和工具定义一样占上下文，而且会一直留在对话历史里，后面每一轮都要重付。一个「列出目录」或者「跑一条 SQL」的工具，很容易一次吐回几十 KB。

–原样返回在后续各轮累计多花

    

    
策略返回给模型的内容token占 200k 窗口

    
截断要留一句「还有多少条、怎么缩小范围」，不然模型以为自己看到了全部。摘要更省，但压掉的信息模型再也看不到了——该返回什么、该压到多细，是写工具的人的设计决定，不是模型能替你做的。
