## 一句话版本

前面几讲里，一个应用只连一个模型，一个任务只交给一个 Agent。真实系统很快会碰到两堵墙：一个模型**不够便宜、不够稳**，一个上下文**装不下、跑不快**。对付前一堵墙，在应用和各家模型之间加一层**网关**，由它决定每个请求发给谁、失败了怎么办；对付后一堵墙，让一个**主 Agent** 把任务拆开，派给几个**子 Agent** 并行做，每个子 Agent 只把结论交回来。两样东西都不神秘，都是在用复杂度换钱、换稳定、换速度，所以都要先算清楚值不值。

## 网关：所有请求先过这一层

<figure class="clip"><video src="/videos/gateway-orchestration/GatewayRouting.webm" poster="/videos/gateway-orchestration/GatewayRouting.png" controls loop muted playsinline preload="metadata"></video></figure>

不加网关时，代码里每个调用模型的地方都直接写着某一家的地址、某一家的报文格式和某一把 API key。换一家模型要改所有调用点，某家限流了只能看着请求失败，月底也说不清钱花在了哪个功能上。

**LLM 网关**是夹在应用和模型之间的一层代理。应用只认它一个入口，剩下的事它来做：

1. **统一接口**：应用永远按同一种格式发请求（常见的是兼容 OpenAI 的 chat completions 格式），网关负责翻译成各家的格式。工具调用一讲里 Anthropic 和 OpenAI 两种报文的差别，就是在这一层抹平的。
2. **路由**：按规则决定这个请求发给谁。可以按难度（便宜模型先答，难题升级到强模型）、按延迟和可用性（谁现在快、谁现在没挂）、按数据合规（含个人信息的请求只能发给某个地区部署的模型）。
3. **重试与降级**：主模型超时或返回 HTTP 429（被限流）时，按退避间隔重试，或者直接切到备用模型。
4. **限流与配额**：给每个团队、每个用户、每把虚拟 key 设请求数和 token 上限，防止某个失控的 Agent Loop 一晚上把预算烧光。
5. **缓存**：一字不差的请求直接返回上次的结果。
6. **统一记账与 trace**：每个请求的模型、token、费用、耗时都在这里记一笔。上一讲的 trace 树，模型调用那一层的 span 天然适合在网关这里打。

常见的网关形态（2026 年 10 月 19 日查证）：**LiteLLM** 是开源的代理，自己部署在自己的服务器上；**OpenRouter** 是托管服务，一个 API 接入很多家模型；**Cloudflare AI Gateway** 跑在 Cloudflare 的全球网络上，提供缓存、限流、重试和降级；Portkey、Kong AI Gateway 等也提供类似功能。功能清单大同小异，区别主要在自己部署还是用别人的服务、数据经不经过第三方。

## 路由：便宜模型先试，没把握再升级

Anthropic 在《Building effective agents》里描述 routing 这种 workflow 时举的例子之一，就是把简单、常见的问题交给更小更便宜的模型，难题交给更强的模型。最朴素的实现是**级联**：小模型先答，同时给出它对这个答案有多大把握；把握低于阈值，就把请求升级到下一档。

实验 00 用三档示例模型算了这笔账。难题占 30% 时，全用大档每 1000 个请求 $14.0、正确率 90.3%；全用小档只要 $0.36，正确率 48.0%；先小后大（阈值 0.8）是 $7.00、85.6%，花一半的钱拿到大部分的正确率。注意被升级的请求要付两到三次钱，难题一多，级联反而不如直接用大档：难题占 60% 时，同一个阈值下级联要 $11.1，正确率 77.8%，比全用大档的 80.7% 低，钱也只省了两成。

级联能不能省钱，关键不在大模型多强，而在**小模型知不知道自己不知道**。自评把握和真实正确率对不上，该升级的没升（答错了），不该升的升了（白花钱）。实践中这个信号可以来自模型自评、输出的 token 概率，或者一个专门训练的分类器，上线前都要拿 eval 集校准。

## 降级、限流与缓存

**重试只救得了「下一次可能就好」的错误。** 429 限流是暂时的，退避一会儿再试多半能成；模型整段不可用时，重试三次就是多等三次超时。实验 01 里主模型可用率 90%、限流 10%、重试 2 次、超时 10 s：只有主模型时成功率 90.0%，P95 耗时 31.5 s，正好是「三次超时加两次退避」；加上备用模型，成功率 99.96%，P95 降到 12.2 s；再把超时缩到 3 s，P95 降到 5.2 s。没有备用时成功率有解析解：可用率 × (1 − 限流概率<sup>重试次数 + 1</sup>)，模拟结果和它对得上。

**两种缓存要分清**：

- **响应缓存**（网关做）：以完整请求为键，一字不差才命中，命中时整个调用都省了，连等待都没有。代价是只适合确定性的问题：温度不为 0 的创作、和时间有关的问题（「现在几点」「今天的新闻」）缓存了反而错。有的网关还提供「语义缓存」，意思相近的问题也算命中，更省，也更容易答非所问。
- **Prompt cache**（模型服务商做，上下文窗口一讲讲过）：缓存的是前缀的计算结果，每一次真正发生的调用都能用，但只省重复前缀那部分输入的钱。

实验 02 里重复率 30%、有效期 1 小时，响应缓存命中 20%，费用从 $144 降到 $115；再加上 prompt cache（2000 token 的系统提示按 0.1 倍计），降到 $72。两者叠加，不互相替代。

## 多 Agent 编排：主 Agent 拆，子 Agent 做

<figure class="clip"><video src="/videos/gateway-orchestration/OrchestratorWorkers.webm" poster="/videos/gateway-orchestration/OrchestratorWorkers.png" controls loop muted playsinline preload="metadata"></video></figure>

Agent Loop 一讲末尾提过：一个主 Agent 把任务拆开，派给几个子 Agent 各转各的循环，再把结果汇总，本质上还是那个循环，只是「工具」变成了另一个 Agent。《Building effective agents》把它叫做 **orchestrator-workers**：一个中心 LLM 动态地拆分任务，派给 worker LLM，再综合它们的结果；适合事先无法预知需要哪些子任务的复杂任务，比如每次要改好几个文件的编程任务，或者要从多个来源收集、分析信息的搜索任务。它和并行化（parallelization）的区别是子任务不是写死的，而是主 Agent 看了输入再决定。

Anthropic 在 2025 年 6 月的工程文章《How we built our multi-agent research system》里公开了一个真实系统：主 Agent（LeadResearcher）分析问题、制定策略，并行派出 3–5 个子 Agent，每个子 Agent 用自己的上下文和工具去搜，评估结果后把结论交回；简单的事实查找只需要 1 个 Agent、3–10 次工具调用，复杂的调研可能用到 10 个以上子 Agent；最后还有一个专门的 CitationAgent 负责给结论标出处。

它为什么有用，两个原因：

1. **上下文隔离。** 每个子 Agent 从干净的上下文开始，只装自己那份工具结果；交回的是压缩过的结论，不是原始材料。主 Agent 的窗口里只有几段结论，不会被十几万 token 的搜索结果淹没，也就没有 Lost in the Middle 的问题。实验 04 里 6 个子任务、每圈工具结果 3000 token，单 Agent 最长上下文 79K，多 Agent 最长 19K；子任务加到 10 个、每圈 1 万 token，单 Agent 要 409K，超过 200K 窗口，多 Agent 最长才 54K。
2. **并行。** 子 Agent 同时跑，墙钟时间由最慢的那个决定。实验 03 里 4 个子任务（各约 40 s，有快有慢），单 Agent 215 s，多 Agent 92 s，快 2.3 倍。Anthropic 那篇文章说，让主 Agent 并行派子 Agent、子 Agent 并行调工具之后，复杂查询的调研时间最多缩短了 90%。

## 代价：token 成倍、协调开销、交接丢信息

同一篇文章给了两组数字：Agent 通常比普通聊天多用约 4 倍 token，多 Agent 系统比普通聊天多用约 15 倍。他们还发现，在 BrowseComp 评测上，token 用量一项就解释了约 80% 的表现差异；用 Claude Opus 4 做主 Agent、Sonnet 4 做子 Agent 的多 Agent 系统，在内部调研评测上比单 Agent 的 Opus 4 高 90.2%。也就是说，多 Agent 好，很大程度上是因为它**被允许花更多 token**：更多子 Agent、更多搜索、各自独立探索。文章也直说，这只在任务价值足够高、付得起这些 token 的时候才划算。

这一点在实验 03 和 04 里能看得更细。如果工作量完全一样，多 Agent 并不一定多花 token：单 Agent 每转一圈都要把之前所有子任务的结果重发一遍，总量是二次方增长的，子 Agent 只重发自己那份（实验 04 默认设置下总输入 1.03M 对 407K）。但单 Agent 重发的大多是一字不变的前缀，开了 prompt cache 之后输入费用从 $3.09 降到 $0.52，和多 Agent 的 $0.40 已经相差不大。所以省 token 通常不是拆分的理由，**拆分换来的是速度和每个上下文的干净**，而真实系统里多出来的 token，来自它做了更多的事。

另外两项代价：

- **协调开销**：主 Agent 要拆分、写任务说明、读结论、汇总；每个子 Agent 从零开始，先要花几圈熟悉情况（实验 03 的「冷启动」）。只有 1 个子任务时，多 Agent 比单 Agent 还慢。
- **交接丢信息**：子 Agent 交回的是它认为重要的结论，主 Agent 和别的子 Agent 看不到原始材料。任务说明写得含糊，子 Agent 会重复别人的工作，或者漏掉关键的一块。Anthropic 的文章提到，早期版本里子 Agent 拿到「研究半导体短缺」这种简短指令时，常常误解任务、互相重复搜索。

## 何时不该用多 Agent

Anthropic 的文章明确说，需要所有 Agent 共享同一份上下文、或者 Agent 之间依赖很多的领域，目前不适合多 Agent；大多数编程任务里真正能并行的部分比调研少得多。

实验 05 用一个示意模型看这件事：子任务之间的依赖越密，能同时跑的批次越少，每条依赖都要靠结论交接，交接一丢就要返工。6 个子任务、交接丢失率 20% 时，依赖程度 0 加速 4 倍，30% 时只剩 1.46 倍、返工率 14%，超过约 68% 就不如单 Agent 从头做到尾。即使交接从不丢信息，曲线也照样往下走：那部分损失来自「必须等前一个做完」。

所以一个简单的判断：**子任务能不能写成互不相干的几份说明书，交给几个互不认识的人分头做？** 能，就拆；拆完还得频繁互相通气，就别拆，让一个 Agent 带着完整的上下文做。

## 其他几种多 Agent 模式

orchestrator-workers 之外，常见的还有：

- **流水线**：每个 Agent 做固定的一段，输出直接交给下一个（相当于 prompt chaining，每一环换成 Agent）。
- **评审者-执行者**：一个负责产出，一个按标准评审并给反馈，循环到通过为止（《Building effective agents》里的 evaluator-optimizer）。
- **投票**：同一个任务跑几遍，按多数或阈值取结论，适合判断类问题（parallelization 的 voting 变体）。

## 实验里讲了什么

0. **路由与成本**：三档示例模型、4000 个难度不同的请求，比较全用小档、全用中档、全用大档和先小后大级联的费用与正确率，可调难题比例、升级阈值和自评噪声。
1. **降级与重试**：20000 个请求的蒙特卡洛，调主模型可用率、限流概率、重试次数和超时，看有无备用模型时的成功率和 P95 耗时，和解析解对照。
2. **缓存**：调请求重复率和缓存有效期，看响应缓存命中率、省下的调用和费用，以及再叠加 prompt cache 的效果。
3. **orchestrator-worker 时间线**：子任务数、耗时、耗时差异和冷启动，单 Agent 串行与多 Agent 并行的甘特图、墙钟时间和总 token。
4. **上下文隔离**：每一次模型调用的输入长度，单 Agent 一路堆高，子 Agent 各自只装一份；最长上下文、总输入 token，以及有无 prompt cache 的费用。
5. **何时不该拆**：示意模型，子任务依赖程度和交接丢失率决定加速比和返工率，找出拆分不再划算的那个点。

## 和前后两讲的关系

Agent Loop 一讲给出了单个 Agent 的循环，并预告了 orchestrator；上下文窗口一讲讲了窗口会满、中间会被忽略，这一讲的上下文隔离就是对它的一种回答。上一讲 Trace 与 Eval 在这里变得更必要：一个请求可能经过网关重试、降级到备用模型，一个任务可能分给五个子 Agent，没有 trace 根本说不清哪一步出了问题，而路由阈值、要不要拆分，都要靠 eval 集来定。下一讲「框架全景」会看到，市面上的 Agent 框架和 SDK 大多就是把这几讲手写过的东西（工具调用、循环、上下文管理、RAG、MCP、流式、trace、网关、子 Agent）打包成了现成的部件。
