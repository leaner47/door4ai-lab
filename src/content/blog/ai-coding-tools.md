## 一句话版本

以前用 AI 写代码，是在聊天框里描述问题，把它给的代码复制回自己的文件，运行，报错了再把报错贴回去。Claude Code、Codex 这类工具把这几步交给了 AI 自己：**它直接在你的项目文件夹里读文件、改文件、跑命令，看到结果不对就接着改，直到做完。**你从「搬运工」变成了「提需求和验收的人」。

## 从聊天框到你的项目里

区别不在模型更聪明，而在 AI 手里多了工具。聊天框里的 AI 只看得到你贴给它的那几行，也没法运行代码；这类工具能自己打开项目里的任何文件，能在你的电脑上执行 `npm test`、`git diff` 这样的命令，所以它能自己发现「我刚写的代码跑不通」。

常见的几款（2026-10-19 核实）都不止一种形态：

| 工具 | 出自 | 能用的形态 | 项目说明文件 |
| --- | --- | --- | --- |
| Claude Code | Anthropic | 命令行（终端里输入 `claude`）、VS Code / JetBrains 插件、Claude 桌面应用、网页版（连上 GitHub 仓库，在云端跑） | `CLAUDE.md` |
| Codex | OpenAI | 命令行（`codex`）、IDE 插件、桌面应用（macOS、Windows）、云端（Codex Cloud，在隔离容器里跑） | `AGENTS.md` |
| Cursor | Anysphere | 基于 VS Code 改的编辑器，内置 Agent 模式；也有命令行版本和云端 Agent | `AGENTS.md` 或自己的规则文件 |

形态不同，做的事一样。命令行和插件版在**你的电脑上**动你的文件；云端版在一台临时的云服务器上把仓库拉下来改，做完交给你一个分支或 Pull Request。Claude 和 Codex 的安装包，课程网站的 Resource 里有下载。

## 它本质上是一个 Agent

拆开看，这类工具只有三样东西：

1. **一个大模型**：负责读懂需求、决定下一步做什么、写出代码。
2. **几样工具**：读文件、改文件、搜索、执行命令。模型自己不能碰你的电脑，它只能说「我要读 `app.js`」，由工具真正去读，再把内容交回给它。
3. **一个循环**：读 → 改 → 跑 → 看结果 → 再改，一直转到它认为做完了，或者需要问你。

模型 + 工具 + 循环，就是 **Agent**。它和聊天机器人的区别是能自己行动、看到行动的结果、再决定下一步。工具具体怎么调用、循环什么时候停、上下文装满了怎么办，课程最后的 Agent 篇会一讲一讲拆开，这里先建立一个画面就够了。

## 用之前要知道的四件事

**它在哪个目录里工作。** 你在哪个文件夹里启动它，它就以那个文件夹为「项目」：在里面读写文件、执行命令。所以先 `cd` 到项目文件夹再启动，别在桌面或用户主目录里启动，否则它看到的是你整台电脑。

**它能执行什么命令。** 每个工具都有权限模式，决定哪些动作自动执行、哪些先问你。以 Claude Code 为例，有「每步都问」（Manual）、「自动改文件」（acceptEdits）、「先出计划」（plan）、由另一个模型在后台把关的 auto 等几档；Codex 用沙箱（只读 / 只能写项目文件夹 / 完全访问）加审批策略（越界时问你 / 从不问）组合。规律是一样的：读文件最安全，改文件次之，跑命令、联网、删东西、推送到远端越来越需要你点头。刚开始用，选会问你的模式，看清它每一步要干什么。

**用 Git 兜底。** 这是 Git 那一讲最实际的用处：**每次让 AI 改之前，先 `git commit` 存个档。** 它改完，用 `git diff` 看它到底改了什么；改坏了，`git restore` 一步回到改之前。没存档就让它改，改坏时你自己之前写的东西也可能一起退不回来。

**项目说明文件。** 在项目根目录放一个 `CLAUDE.md`（Claude Code 读）或 `AGENTS.md`（Codex、Cursor 等读），写上项目的规矩：用什么命令跑测试、代码风格、哪些目录不要动。工具每次启动会自动读它，相当于给新来的同事一份入职须知，不用每次重复交代。

## 怎么提需求

AI 不知道你脑子里的标准，你没说的，它就自己猜。一条好需求至少说清四件事：

- **目标**：要做成什么样。「在标题下面加一个深色模式按钮，点一下切换深浅色」，而不是「把网页改好看一点」。
- **范围**：改哪些文件，哪些不要动。
- **约束**：不许做什么，要保持什么。比如「不要引入新的库」「保持现有函数名不变」。
- **验证**：怎么算做完。「跑 `npm test`，全部通过才算完成」。

再加三个习惯：**一次一件事**，做完一件验证一件；复杂的改动**让它先读、先说计划**，计划不对在它动手前就纠正；**让它自己跑测试**，有报错它会自己看着修。

## 常见的坑

- **它会自信地写错。** 代码看起来很像样，语气也很笃定，但就是跑不通。所以一定要跑起来验证，不能只看它说「完成了」。
- **它会改你没让它改的地方。** 让它改一个函数，它顺手「优化」了另一个，甚至删掉了它认为没用的代码。所以每次都要看 diff，只批准你看懂的改动。
- **它会编造不存在的东西。** 调用一个库里根本没有的函数，或者引用一个不存在的配置项。跑一下就会报错，这也是为什么验证这一步省不掉。

三个坑的解法都一样：**看 diff、跑起来、出了问题用 Git 退回去。**工具越来越聪明，但最后为代码负责的是你。

## 实验里讲了什么

0. **全过程回放**：给网页加深色模式按钮，逐步看 AI 读文件、提计划、改三个文件、跑测试失败、看报错找原因、再改、通过。回放是预设的，每一步的 diff 是页面真实算出来的。
1. **diff 怎么看**：页面用最长公共子序列逐行比较改前改后，红色是删掉的行，绿色是加上的行；可以切换成 `git diff` 的格式，也可以自己改右边的文本。
2. **权限**：读文件、改文件、`npm install`、`rm -rf`、`git push` 等命令，在三种模式下分别是自动执行、先问你还是拒绝（示意规则），也可以输入自己的命令看规则怎么判断。
3. **Git 安全网**：先 commit 再让 AI 改，和直接让 AI 改，两种顺序的结局对比。测试是页面真的执行代码跑出来的，`git diff` 的格式和提交编号也是真实计算的。
4. **需求写得好不好**：用目标、范围、约束、验证四项检查清单给需求打分，看模糊需求和清楚需求差在哪；这是关键词规则，不是 AI 评分。

## 和前后两讲的关系

这一讲把前面几讲接了起来：Git 那一讲的提交、diff 和回退，在这里成了让 AI 动手的安全网；Cloudflare 那一讲说的「push 之后自动部署」，意味着 AI 改的代码可能很快就到了线上，所以提交前看 diff 更重要。
