## 一句话版本

一个 Agent 跑完一次任务，你手里通常只剩最终回答。但中间它调了几次模型、几次工具、哪次报错重试、哪一步花了最多时间和钱，全都看不见。**trace** 就是把这次运行的每一步按父子关系记下来，得到一棵树；**eval** 是在这棵树上打分：不只问「最终答案对不对」，还问「走的路对不对」「每一步做得对不对」。有了这两样，改 prompt、换模型、加工具之后，你才知道是变好了还是改坏了。

## 一次运行是一棵 span 树

<figure class="clip"><video src="/videos/trace-eval/TraceTree.webm" poster="/videos/trace-eval/TraceTree.png" controls loop muted playsinline preload="metadata"></video></figure>

trace 里的基本单位叫 **span**：一段有开始、有结束的工作。span 可以嵌套，于是一次 Agent 运行自然长成一棵树：

- 最外层是整个任务（invoke_agent）；
- 往下是 Agent Loop 的每一轮，每轮先有一次模型调用（chat）；
- 模型要调工具，这一轮下面再挂几个工具调用（execute_tool），并行的就并排挂着。

每个 span 记录同样几样东西：**输入、输出、开始时间、耗时、token 数、成本、状态（成功或错误）**。把这棵树横过来、按时间画成甘特图，一眼就能看出：哪些步骤是并行的，整轮在等谁，哪一步最慢。

拿实验 00 的例子来说，任务是「比较北京和上海明天的天气，写一段 100 字以内的出行建议」，最终回答完全正确。但 trace 里能看到，第 1 轮查上海天气超时了一次，重试才拿到结果，整轮因此多等了约 1 s。只看最终回答，这件事根本不存在。

这棵树的字段名正在被标准化。OpenTelemetry（分布式追踪的通用标准）有一套 GenAI 语义约定：模型调用、工具调用、Agent 运行分别用 `gen_ai.operation.name` 取值 `chat`、`execute_tool`、`invoke_agent` 标注，token 数记在 `gen_ai.usage.input_tokens` 和 `gen_ai.usage.output_tokens`，模型名记在 `gen_ai.request.model`。2026-10-19 查证时，这套约定已从 OpenTelemetry 主仓库移到单独的 semantic-conventions-genai 仓库，仍处于 Development（尚未稳定）状态，字段名还可能改。各家可观测性工具和 Agent 框架的嵌套方式也不完全一样，但「任务 → 模型调用 → 工具调用」这个层次是共通的。

## 时间和钱花在哪了

有了 span 树，就能做归因。实验 01 把同一条 trace 的墙钟时间按「模型调用 / 工具执行 / 检查 / 编排与等待」切开：在每个时刻，有模型在跑就算模型的，否则有工具在跑就算工具的。这个例子里模型调用占了 71%，最后一轮写摘要的 chat 既最慢（3.31 s）又最贵（约占总成本的 45%）：它的输出 token 最多，而输出 token 是一个个生成的，单价又高。

两个容易被忽略的点：

1. **并行改变的是墙钟时间，不是总工作量。** 同一轮的两次工具调用并行时，这一轮的工具时间取最长那条线；改成串行就是全部相加。实验里关掉并行，墙钟时间从 9.27 s 变成 10.39 s。
2. **慢和贵不是一回事。** 一次超时让整轮多等了一秒，却一分钱没花；只看账单发现不了，只看耗时又会漏掉 token 爆涨的那一轮。两个维度要分开看。

## 为什么 Agent 比单次调用难测

「模型评测」一讲讲过给单次调用建一套小 eval：几十道题、一条判分规则、每次改动重跑。Agent 难在三处：

- **多步。** 一次运行有十几个 span，最终答案错了，问题可能出在任何一步；最终答案对了，中间也可能有一步是错的、碰巧没造成后果。
- **不确定。** 同一个任务跑两次，模型可能选不同的工具、不同的顺序、不同的轮数。不能拿一条「标准轨迹」逐字比对。
- **路径不同，结果也可能都对。** 先查北京再查上海，和两个一起查，都是对的。判分规则要允许合理的变化，又要抓住真正的错误。

所以 Agent 的 eval 通常分三层来做。

## 三层 eval：结果、轨迹、单步

1. **结果（end-to-end）**：只看最终产出，任务完成了没有。最接近用户的感受，但看不到过程。
2. **轨迹（trajectory）**：看中间的调用序列合不合理：有没有调错工具、调了不需要的工具、重复调用、漏掉必需的步骤、轮数是否超限。它不要求和某条标准轨迹一模一样，而是检查一组规则。
3. **单步（unit）**：单独看某一步：这次工具调用的参数对不对，这次检索返回的是不是相关内容，这一步的输出格式能不能被下一步解析。

实验 02 用同一个天气任务的 10 条运行记录，三种判分都是页内真实执行的程序。默认设置下结果、轨迹、单步的通过率分别是 60%、60%、80%，而 10 条里有 8 条，结果判分和过程判分（轨迹 + 单步）的结论不一致。分歧集中在两类：

- **结果对、过程差**：先去搜了一遍网页、重复查了北京、一次只查一个城市拖到 5 轮。这次碰巧答对了，但更慢更贵，换个任务就可能出错。
- **过程全对、结果错**：工具都调对了，最后把 23 °C 抄成了 21 °C，或者把「上海更暖」说成「北京更暖」。只有看最终输出的判分抓得到。

三层各抓一类问题，缺了哪一层都会漏。

## 判分方法：规则、程序、LLM 裁判

三层 eval 用什么来判，按可靠程度排：

1. **精确匹配与规则**：答案是不是某个值、有没有包含关键字段、字数是否超限、有没有调某个工具、轮数是否超过 <i>N</i>。便宜、确定、可复现，能用就用。
2. **程序检查**：直接验证 Agent 造成的后果。写代码的 Agent 就跑测试；操作数据库的就去查表里的状态是不是改对了；订票的就看订单系统里是否真有这张票。SWE-bench 这类代码 Agent 评测就是靠跑项目自己的测试判分。这比读 Agent 的回答更可靠：它说「已完成」不算，世界真的变了才算。
3. **LLM-as-judge**：开放式的输出（一段建议、一封邮件）没有标准答案，就让另一个模型按评分标准打分，或者在两个回答里挑更好的。便宜、快，但有系统性偏差。

LLM 裁判已知的偏差主要有两种。**位置偏好**：两个回答谁排在前面，就更容易被选中。**长度偏好**：更长的回答更容易被判为更好，哪怕多出来的只是废话。

实验 03 模拟了一个同时有这两种偏好的裁判，对 200 对已知优劣的答案打分，重复 400 组。常用的校准办法是**交换顺序各判一次，两次一致才采纳**。结果有一个值得停下来想的地方：

- 位置偏好 0.3、无长度偏好时，判一次的准确率约 75%；交换判两次后，60% 的对子结论一致，这些一致结论的准确率约 91%。
- 但如果把不一致的都记成平局 0.5 分，期望得分和判一次**完全一样**，数学上恰好相等。

也就是说，交换顺序不会让裁判变聪明，它的价值是**把靠不住的结论筛出来**：一致的可以直接用，不一致的交给人或更强的裁判。再把长度偏好也拉上去，一致结论的准确率会降到约 82%：长度偏好两次都选同一个更长的回答，交换顺序抓不住它。对付长度偏好要靠别的办法：评分标准里写明不按长度给分、对长度做统计校正，或者定期抽一批人工标注，核对裁判和人的一致率。

## 回归测试：改了之后，哪些题由过变挂

<figure class="clip"><video src="/videos/trace-eval/RegressionGrid.webm" poster="/videos/trace-eval/RegressionGrid.png" controls loop muted playsinline preload="metadata"></video></figure>

eval 集最常用的场景是回归测试：改 prompt、换模型、加工具之后，在**同一套题**上把新旧两版都跑一遍，逐题比较。重点不是总分，而是四格计数：

| | 新版通过 | 新版失败 |
|---|---|---|
| 旧版通过 | 都过 | **过 → 挂（退化）** |
| 旧版失败 | **挂 → 过（修好）** | 都挂 |

实验 04 有两个例子。「改 prompt」：新旧两版都是 21/30，可是有 5 道题由过变挂、5 道由挂变过，多步比较类退化了 3 道，输出格式类修好了 3 道，总分把这些变化全部抵消了。「换模型」：总分从 21 涨到 25，但拒答与安全类从 4 掉到 2。这种退化往往一票否决，总分涨得再多也不能上线。

还有一个问题：变化是不是真的？模型输出本身有随机性，同一版本跑两次也会有几道题翻转。只看翻转的那些题，用 McNemar 检验估计「这么多题单向翻转」靠不靠得住：5 比 5 时 <i>p</i> = 1，完全看不出差别；2 比 6 时 <i>p</i> ≈ 0.29，也还不能说新版更好。题少的时候，要么每题多跑几次取多数，要么扩充题目，再下结论。

## 拦截：在危险动作发生之前

eval 是事后打分，有些错误等不到事后：删了数据库、把密钥发到了外面，再打分也晚了。所以在 Agent Loop 里，工具调用真正执行之前，还要过一道**拦截（guardrails）**：

- **输入检查**：用户输入和工具返回的内容里，有没有藏着「忽略之前的指令」这类注入。
- **工具调用前检查**：只读白名单直接放行；写操作暂停，等人确认；命中危险命令黑名单（删根目录、DROP 表、下载脚本直接执行、强制推送）、读取密钥文件、往外发密钥的，直接拦截。
- **输出检查**：最终回答发出去之前，检查格式、长度、有没有泄露不该说的东西。实验 00 那条 trace 最后的 output_check 就是一道输出检查。

实验 05 把 16 条工具调用请求交给一个页内规则引擎逐条判定，切换宽松 / 平衡 / 严格三种策略看结论怎么变。黑名单永远优先，不受策略影响。规则只能拦住写得出来的模式，`rm -r -f` 换个写法就可能绕过去，所以真实系统要同时配沙箱、最小权限和人工确认，规则只是第一道。

## 线上：采样 trace，持续打分

上线以后，eval 不会停：

1. **全量记 trace**，至少记 span 结构、耗时、token 和错误；完整的输入输出量大、可能含隐私，可以只对一部分请求保留。
2. **抽样打分**：每天从线上 trace 里抽一批，用同样的三层判分自动评一遍，看通过率有没有掉。
3. **把失败变成题**：线上抓到的失败案例补进 eval 集，下次改动时它就是回归测试的一道题。

这样 eval 集会越来越贴近真实流量，也就越来越难被「针对性优化」骗过。

## 实验里讲了什么

0. **一条 trace 的树**：天气对比 Agent 一次运行的 span 树与甘特图，可折叠，点任何一个 span 看输入输出、token、耗时和成本。
1. **成本与耗时归因**：墙钟时间按模型 / 工具 / 检查 / 等待分解，找出最慢和最贵的 span，可改单价、切换工具并行与串行。
2. **三层 eval**：10 条运行记录分别用结果、轨迹、单步三种程序判分，看通过率和哪些运行的判分互相矛盾。
3. **LLM 裁判偏差**：模拟有位置偏好和长度偏好的裁判，蒙特卡洛看准确率分布，以及交换顺序判两次能筛掉什么、筛不掉什么。
4. **回归对比**：两版在 30 道题上的逐题结果矩阵、四格计数、各题型变化和 McNemar 检验，可以点格子改结果。
5. **拦截**：只读白名单、写操作确认、危险命令黑名单三类规则逐条判定工具调用，也可以自己输入一条。

## 和前后两讲的关系

「模型评测」一讲给单次模型调用建了一套小 eval；「Agent Loop」一讲把模型调用放进了循环。这一讲把两者接起来：循环的每一圈都记成 span，评测从「最终答案对不对」扩展到「每一步、整条路径对不对」，并在循环里加上执行前的拦截。下一讲「多模型网关与多 Agent 编排」里，请求会在多个模型和多个 Agent 之间转发，trace 树会跨越多个服务；没有这一讲的 trace 和 eval，那种系统出了问题几乎无从查起。
