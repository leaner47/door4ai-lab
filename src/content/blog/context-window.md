## 一句话版本

模型没有记忆，它只有一个**上下文窗口**：这次调用送进去的全部 token，就是它此刻知道的全部。系统提示、工具定义、每一轮对话、每一次工具返回、检索来的片段，统统排在这条长度有限的带子上。带子不会变长，所以 Agent 工程的一大半功夫，是决定**往里塞什么、什么时候丢什么、不该放在窗口里的东西记在哪**。

## 窗口里到底有什么

上一讲的 Agent Loop 每转一圈，都把新的东西追加进对话：模型的回复、它要调的工具、工具返回的结果。把一次调用送进模型的内容摊开看，是五类：

<figure class="clip"><video src="/videos/context-window/ContextBudget.webm" poster="/videos/context-window/ContextBudget.png" controls loop muted playsinline preload="metadata"></video></figure>

1. **系统提示**：角色、规则、格式要求，一般几百到几千 token。
2. **工具定义**：每个工具的名字、说明和参数 schema。工具一多，几十个工具就是上万 token，而且每一轮都在。
3. **历史消息**：你说过的、它答过的，一轮不落。
4. **工具结果**：读文件、查数据库、搜网页返回的原文。这是最容易失控的一类，一次 `cat` 一个大文件就是几万 token。
5. **检索片段**：从知识库里按问题取回的几段文字（下一讲 RAG）。

它们都是同一种东西：token。模型的输出也要占窗口，所以输入必须给输出留出空间。超了就不是「效果变差」，而是请求直接被拒绝。实验 00 的容量条可以拖着玩。

各家模型的窗口有多大？下面是 2026 年 10 月 16 日查官方文档的结果：

| 模型 | 上下文窗口 | 单次最大输出 |
|---|---|---|
| Claude Opus 5.5 / Sonnet 5.5 / Haiku 5.5 | 1M token（上一代为 200K） | 128K |
| GPT-5.4 | 1,050,000 token | 128K |
| GPT-5.5 | 1M token | — |
| Gemini 4 Argon | 1,048,576 token（输入输出合计） | 65,536（长解码模式可到 1M） |
| Llama 4 Scout / Maverick（开源权重） | 10M / 1M token | — |
| Llama 3.1（开源权重） | 128K token | — |

数字在变大，但它们不改变下面要讲的三件事：长度要花钱，中间的东西会被忽略，会话一结束窗口就清空。

## 为什么不能一直塞：越长越贵、越慢

KV Cache 那一讲算过显存：每个 token 在每一层都要存一份 K 和一份 V。Llama-3-70B 是 80 层 × 8 个 KV 头 × 128 维，bf16 下每个 token 约 328 KB，128K 上下文就是 43 GB，超过一张 H100 显存的一半，还没算模型权重。这是**线性**的：长度翻倍，显存翻倍。

计算量更糟。注意力里每个 token 都要和前面所有 token 算一次相似度，<i>n</i> 个 token 就是 <i>n</i>² 对：

<p class="formula">注意力计算量 ≈ 4 · <i>n</i>² · <i>d</i> · 头数 · 层数　　矩阵乘法计算量 ≈ 2 · 参数量 · <i>n</i></p>

左边是**平方**的，右边是线性的。实验 01 里可以看到，对 Llama-3-70B 来说，上下文在 5 万 token 左右以前，矩阵乘法占大头；过了这个点，注意力反超，到 128K 时已经是矩阵乘法的 2.4 倍，到 1M 是 19 倍。这就是为什么 1M 窗口的模型存在，但把一整本书塞进去每次都要等几十秒、花几十倍的钱。服务商的定价也反映这一点：有的模型对超过某个长度的请求按更高的单价收费。

所以「窗口够大」从来不是「全塞进去」的理由。

## Lost in the Middle：装得下，不等于看得见

2023 年 Liu 等人做了一个干净的实验：问模型一个问题，给它 20 篇文档，其中只有一篇包含答案，然后把这篇放在第 1、5、10、15、20 的位置。结果是一条 U 形曲线：放在开头，正确率 75.8%；放在结尾，63.2%；放在中间，掉到 53.8%，比**根本不给文档、让模型闭卷回答**的 56.1% 还低。也就是说，关键信息埋在长上下文的中间时，模型几乎等于没看见它。

这个现象在后来的模型上减轻了，但没有消失。它对上下文工程的含义很直接：

- 最要紧的规则放系统提示的开头，不要藏在第 40 条。
- 当前任务、最新的用户要求放在最末尾。
- 一大段工具结果塞进来之前先裁剪：只留相关的部分，别让关键的两行淹在中间。

## 上下文工程：放什么、怎么排、怎么压

Agent 跑几十轮以后，历史和工具结果迟早把窗口填满。到那时只有三条路，实验 03 把它们放在同一段 40 轮对话上比较：

- **截断**：删掉最早的轮次。最简单，也最危险：用户第 2 轮说的「不能用 Python 3.13」会在第 8 轮被悄悄删掉，Agent 从此不知道这条规则存在。
- **滚动窗口**：永远只留最近 <i>k</i> 轮。占用稳定，但和截断一样，早期信息注定丢。
- **摘要**：占用到一定比例时，让模型把前半段压成一段几百 token 的总结，再接着跑。关键事实可以保住，但代价是多一次调用，而且细节会在总结里被磨平。

现在的 API 已经把其中一部分做成了服务端功能：比如自动清掉旧的工具结果、在逼近上限时由服务端做摘要（Anthropic 称为 compaction），不必自己写。但原理没变：窗口不会变大，只能决定留什么、丢什么。

## 记忆的三层：工作记忆、持久记忆、外部知识

把前面的事放在一起看，Agent 的记忆其实是三层：

<figure class="clip"><video src="/videos/context-window/MemoryLayers.webm" poster="/videos/context-window/MemoryLayers.png" controls loop muted playsinline preload="metadata"></video></figure>

1. **工作记忆**就是上下文窗口。每次调用都看见，但有上限、越长越贵，而且会话一结束就清空。
2. **持久记忆**在窗口外面：一个文件、一张表。会话结束前把要紧的几行写进去（用户是谁、项目用什么、做到哪了），下次开始时读回来。实验 04 模拟了两天的会话：第二天开头读一个 100 多字的 `memory.json`，就能接着干；不读，模型只能反问，或者你得把第一天的对话整段塞回去。你在用的 AI 编程工具里的 `CLAUDE.md`、`AGENTS.md`，还有聊天产品的「记忆」功能，都是这一层。
3. **外部知识**量太大，不可能放进窗口，也不该放进记忆文件。它留在外面，每次按问题检索，只把相关的几段带回窗口。这就是下一讲的 RAG。

三层的原则是一样的：窗口里只放现在要用的。

## Prompt cache：固定前缀只付一次全价

最后一件事关乎钱。每一轮的输入都是「同样的前缀 + 末尾新增的一小段」：系统提示和工具定义一字不变，历史只在后面追加。KV Cache 那一讲说过，前文不变则它的 K、V 就不变，所以服务商可以把算过的前缀存起来，下一轮直接复用，只收很低的「读缓存」费用。

查证时（2026 年 10 月 16 日）的公开计价：Claude 的缓存读取是基础输入价的 0.1 倍，写入是 1.25 倍，最新几款模型读取更低到 0.05 倍甚至 0.025 倍；GPT-5.4 的缓存输入是 \$0.25 / 百万 token，对应普通输入 \$2.50 的 10%。实验 05 按 0.1× / 1.25× 算：20K 前缀、每轮新增 1K、跑 30 轮，累计输入 106 万 token，不用缓存 \$3.20，用缓存 \$0.49，省 85%。

要吃到这个便宜，前缀必须**一字不差**地固定。在系统提示开头放一个时间戳或随机数，每轮前缀都不同，缓存就全废了。所以上下文的排法有了第二条理由：固定的放前面，变化的放后面，这既是 Lost in the Middle 的要求，也是省钱的要求。

## 实验里讲了什么

0. **窗口里有什么**：五种内容各一个滑块，拖到超过窗口，超出的部分变红，读数显示谁占大头、还剩多少给输出。
1. **长度与代价**：按 Llama-3-70B 真实算 KV cache 显存（线性）和注意力计算量（平方），看注意力在约 5.4 万 token 处反超矩阵乘法。
2. **Lost in the Middle**：拖关键事实在 20 块内容里的位置，示意曲线拟合论文的五个实测点，中间最低。
3. **三种压缩策略**：40 轮对话、固定种子的长度，截断 / 滚动窗口 / 摘要三条占用曲线，下面标出第 2 轮的关键事实是否还在。
4. **持久记忆**：一步步走完两次会话，看写入 `memory.json` 再读回来和不读的区别，以及第二次会话开头要带多少上下文。
5. **Prompt cache**：固定前缀、每轮新增、轮数三个滑块，累计费用两条曲线。
