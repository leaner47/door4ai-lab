## 一句话版本

模型本身只做一件事：读进一段文字，写出一段文字。它不能读文件、不能跑命令、记不住上一轮，也不知道自己写的命令有没有被执行。这些能力全部来自包在它外面的一段程序，这段程序叫 **harness**。所以：

$$
\text{Agent} = \text{模型} + \text{harness}
$$

模型负责「下一步做什么」，harness 负责把这个决定变成真实的动作，并且在它失控时拦住它。你用的 Claude Code、Codex、Cursor，本质上都是 harness。

## 名字从哪来

Harness 的本义是马具：套在马身上、把马的力气变成拉车动力的那一整套皮带和挽具。马决定往哪儿使劲，车能不能动、往哪个方向走、会不会翻，取决于挽具。

第 105 讲 Agent Loop 最后一节已经点过这个词：循环、工具执行、权限检查、步数和预算、出错处理，合起来就是 harness。这一讲把它当作一个整体来看，后面几讲（上下文、RAG、MCP、编排）都可以读成「harness 的某一个部件」。

## 五个部件

1. **循环**：调一次模型，看它要不要调工具；要，就执行、回填、再调一次；不要，就结束。还要在步数或预算到头时强行停下。（第 105 讲）
2. **工具执行与错误回填**：解析模型输出的 `tool_use`，校验参数，真正去执行；失败时把错误写成 `tool_result` 交回给模型，而不是让程序崩掉。（第 100 讲）
3. **上下文管理**：每次调用前决定窗口里放什么：清掉旧的工具结果、快满时做摘要、把稳定的内容排在前面。（第 110 讲）
4. **权限**：哪些动作自动执行，哪些先问人，哪些直接拒绝；命令在什么沙箱里跑。（《AI 写代码是怎么回事》那一讲的权限模式）
5. **状态与记忆**：任务清单、笔记文件、`CLAUDE.md` 这类持久记忆，让 Agent 在上下文被压缩之后、甚至换一个会话之后还能接着干。（第 110 讲的记忆三层）

实验 00 是一个页面里真实运行的迷你 harness，任务是「把端口从 8080 改成 9090 并让测试通过」。模型用规则模拟，其余全是真的：文件读写、搜索、测试、token 计数、8K 窗口的上限。五个部件逐个关掉，坏法各不相同：

- 没有**循环**，程序拿到第一条 `tool_use` 就结束，什么都没改。
- 没有**工具执行**，模型只能告诉你「请把第 5 行改成……」，文件原封不动。
- 没有**错误回填**，第一次测试失败就被当成异常抛出，循环中断，而这次失败本来正是模型找到第二处要改的地方的线索。
- 没有**上下文管理**，两次搜索各把七十多行旧日志带进窗口，第 6 次调用超出上限，请求被 API 拒绝。
- 没有**权限确认**，模型「顺手」删掉旧日志的那条 `rm` 真的执行了。任务照样完成，测试照样通过，但删了一个你没让它删的文件。

最后一种最值得注意：权限出问题时，结果看起来往往是成功的。

## 它是程序，但会再调一次模型

Harness 的主体是普通的确定性代码：解析 JSON、校验参数、执行命令、数 token、计步数、重试。这些事交给代码，因为代码可预测、可测试，而且不花 token。

但有几个环节需要读懂内容，规则写不出来，harness 就再调一次模型，常常是更小、更便宜的那个：

| 环节 | 为什么非用模型不可 |
|---|---|
| 压缩历史（compaction） | 要判断前 40 轮里哪些事实以后还用得上 |
| 子 agent | 本身就是另一个模型实例，在自己的上下文里干活，只交回结论（第 135 讲） |
| 网页内容提炼 | 先让小模型按问题读一遍长网页，只把要点交给主模型 |
| 安全判断 | 一段藏在网页里的提示注入可以千变万化，规则表挡不住；Claude Code 的 auto 权限模式就是由另一个模型在后台把关 |
| 记忆整理、会话标题 | 判断什么值得长期记住、一句话概括内容 |

分工的原则可以说成一句话：**什么时候做，由程序按规则决定；做出来的内容是什么，交给模型判断。** 拿压缩来说，「上下文超过上限的 60% 就压缩」是一行 `if`，「摘要里留哪几条」是一次模型调用。实验 01 给 14 个 harness 动作分类，可以先自己判断再揭晓。

如果把模型比作 CPU，harness 更像操作系统：内核是确定性的代码，负责调度、权限和资源；它启动的进程里，有一些本身就是模型。

## 按需加载：先给目录，用到再展开

第 100 讲算过，工具定义每一轮都要整份发一遍。工具一多，这笔开销就很可观。Anthropic 2025 年 11 月的一篇工程文章给了实测数字：接上 GitHub、Slack、Sentry、Grafana、Splunk 五个 MCP 服务器，58 个工具的定义大约 55K token，对话还没开始就占掉了。他们的做法叫 **tool search**：工具定义照样交给 API，但标上 `defer_loading`，模型一开始只看见一个「搜索工具」；需要时它先搜，匹配到的几个工具才展开成完整定义进入上下文。文章里的例子从约 77K token 降到约 8.7K，减少约 85%。

同样的思路用在三处：

- **工具**：先放一个搜索工具，用到哪个再加载哪个。
- **Skill**：Anthropic 的 Agent Skills（2025 年 10 月）分三层加载：启动时只把每个 skill 的名字和一行描述放进系统提示；模型判断某个 skill 相关，才去读完整的 `SKILL.md`；`SKILL.md` 里再引用的文件，用到时才打开。
- **文件**：不预先把代码库塞进来，只给路径，让模型自己用搜索和读文件工具去找需要的那几行。

实验 02 用真实分词器数：58 个详细说明的工具、12 个 skill，全部预加载每轮约 4 万 token，按需加载约 3 千。代价是多一次搜索调用，以及模型可能搜不到它真正需要的那个工具。

## 拼请求：稳定的放前面

每次调用模型前，harness 都要把系统提示、工具定义、记忆、历史、最新的工具结果按顺序拼成一个请求。第 110 讲讲过 prompt cache：两轮请求开头完全相同的那一段，服务端可以直接复用，按原价的约十分之一收费。拼法决定了这一段有多长。

实验 04 把相邻两轮请求真实分词，再逐个 token 比较最长公共前缀。正常拼法下，第 13 轮的请求有 94% 和上一轮相同，输入费用约为不缓存时的 17%。然后试三个常见错误：

- 在系统提示开头写当前时间：第一个 token 就不同，缓存全废，费用反而超过不缓存（因为每轮都在重新写入缓存）。
- 每轮按相关度重排工具：工具定义排在前面，一动就打碎后面的一切。
- 把工具定义放到历史后面：历史每轮都在变长，工具定义的位置跟着往后移，这部分每轮都要重算。

所以 harness 拼请求的第一原则是：**稳定的内容放前面，只在末尾追加。**

## 能换模型的 harness，换了为什么不一定好用

有些 harness 和模型是一家做的，比如 Claude Code 之于 Claude、Codex CLI 之于 OpenAI 的模型；有些从一开始就设计成可以接任何模型，比如 Cline、Aider、OpenCode。Codex CLI 也是开源的，配置里同样可以换成其他服务商。能换，是因为中间有一层适配：把 harness 内部统一的工具调用格式，翻译成各家 API 的格式，而现在各家的 function calling 接口已经很接近了。

但「能接上」不等于「一样好用」。最典型的是改文件这件事，不同的 harness 让模型用不同的格式表达：

- **整份重写**：把改后的整个文件写出来。最简单，也最贵，而且模型容易偷懒写一句「其余代码不变」。
- **精确替换**：Claude 的文本编辑工具用的是 `str_replace`，给出一段原文 `old_str` 和替换后的 `new_str`，原文必须在文件里恰好出现一次。
- **补丁**：Codex 用 `apply_patch`，一种以 `*** Begin Patch` 开头、按上下文行定位的 diff 格式。

实验 03 在页面里实现了这三种格式的解析器，对同一份文件做同一处修改，再注入模型常犯的错：缩进多一格，`str_replace` 直接拒绝，`apply_patch` 因为会逐级放宽匹配（先精确，再忽略行尾空格，再忽略首尾空格）仍然能打上；原文只抄一小段，`str_replace` 发现它出现了两处而拒绝；整份重写时偷懒，解析器照样报「成功」，文件却少了三个函数。

哪种格式更好，没有绝对答案，**取决于模型训练时练的是哪一种**。OpenAI 的 Codex 提示指南（2026 年 2 月）写得很直接：强烈建议使用他们原版的 `apply_patch` 实现，因为模型就是在这种 diff 格式上训练的。Aider 的文档也说，不同模型适合不同的编辑格式：Gemini 常常不遵守标准 diff 格式里的代码块写法，所以给它单独配了一种；GPT-4 Turbo 那一代用其他格式时爱写占位注释偷懒，换成简化的 unified diff 才好转。

这也是为什么模型和 harness 越来越分不开：前沿模型在后训练阶段，就是放在自家 harness 的工具集里，用强化学习练出来的（RLHF 那一讲的最后一节）。把它放进一个工具形态不同的 harness，它多半还能用，但出错更多、绕的弯更多。所以：

- 用模型无关的 harness，要接受每个模型都发挥不到极致；好的做法是给不同模型配不同的工具格式和提示，Aider 就是这样做的。
- 自己搭 harness、又打算接多家模型，工具就设计得朴素一点：读文件、写文件、搜索、执行命令。越接近各家模型都练过的形态，换模型时损失越小。

## 实验里讲了什么

0. **拆掉一个部件**：页面里真实运行的迷你 harness（虚拟文件系统、搜索、测试、o200k 分词器计数、8K 窗口），五个部件逐个关掉，看任务在哪一步、以什么方式坏掉。
1. **程序还是模型**：14 个 harness 动作，自己分成「确定性代码」和「再调一次模型」，再揭晓答案和理由。
2. **按需加载**：工具数、说明详细程度、用到几个、skill 数和正文长度，真实分词器计数，对比全部预加载和按需加载每轮占多少窗口；可切换到 Anthropic 文章里 MCP 工具的实测平均长度。
3. **三种编辑格式**：整份重写、`str_replace`、`apply_patch` 三个真解析器作用在同一份文件上，输出可直接编辑，四个按钮注入常见错误，对比能否应用、输出 token 数、结果是否正确。
4. **拼请求与前缀缓存**：相邻两轮请求真实分词，逐 token 求最长公共前缀，三个开关演示时间戳、重排工具、工具放在历史后面怎么打碎缓存。

## 和前后两讲的关系

前两讲分别讲了工具调用和 Agent Loop：模型输出一条 `tool_use`，程序执行、回填、再调一次。这一讲给这段程序起了名字，并把它当作一个整体来看：它有哪些部件、哪些是代码、哪些又是模型。下一讲「上下文窗口」讲的是 harness 最重要、也最花心思的那项工作：窗口里放什么、丢什么、记在哪。再往后的 RAG、MCP、编排，也都是在给 harness 加部件；第 140 讲会看到，各种 Agent 框架就是把这些部件打包好的 harness。
